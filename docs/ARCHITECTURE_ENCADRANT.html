Pixelium Consent Commerce

Document d'architecture — Stage Pixelium 2026
Projet : Commerce agentique avec consentement utilisateur (A2A + mandats AP2-inspired)
Auteur : Stagiaire · Destinataire : Encadrant
Date : Juillet 2026

Résumé exécutif : Nous avons développé un prototype de boutique en ligne où des agents IA peuvent rechercher des produits et effectuer des achats uniquement après validation explicite de l'utilisateur. Chaque transaction suit une chaîne de mandats signés : Intent → Cart → Payment. Un broker central valide tout avant qu'un agent de paiement ne débite (simulation). Un assistant RAG (embeddings + vector store + LLM) aide l'utilisateur à choisir quoi acheter.

1. Contexte et objectifs

1.1 Problématique

Les assistants IA peuvent aujourd'hui rechercher des produits, remplir un panier et parfois initier un paiement sans contrôle clair pour l'utilisateur. Notre projet démontre qu'il est possible d'automatiser l'achat tout en conservant le consentement humain à chaque étape critique.

1.2 Objectifs du prototype

  • Implémenter une chaîne de mandats inspirée du protocole AP2 (Agent Payments Protocol, Google).
  • Faire communiquer deux agents via le protocole A2A (Agent-to-Agent).
  • Centraliser la validation dans un Consent Broker.
  • Proposer un assistant IA avec RAG pour recommander des produits du catalogue.
  • Journaliser toutes les opérations dans une piste d'audit.

4. Chaîne de mandats (consentement)

Inspirée du protocole AP2, chaque achat suit trois mandats signés et liés :

  UTILISATEUR                    MARCHAND                 BROKER              AGENT PAIEMENT
      │                             │                       │                      │
      │── Intent Mandate ──────────►│                       │                      │
      │   (signé utilisateur)       │                       │                      │
      │                             │── Cart Mandate ──────►│                      │
      │                             │   (signé marchand)    │                      │
      │── Payment Mandate ──────────┼──────────────────────►│── validate chain ──►│
      │   (signé utilisateur)       │                       │                      │

4.1 Structure d'un mandat

{
  "id": "uuid",
  "type": "intent | cart | payment",
  "version": "1.0",
  "createdAt": "ISO-8601",
  "expiresAt": "ISO-8601",
  "payload": { ... },
  "signerId": "user | merchant | ...",
  "signature": "HMAC-SHA256 hex",
  "parentMandateId": "lien vers mandat parent"
}

4.2 Signature

Algorithme : HMAC-SHA256 sur la chaîne canonique :

type | signerId | parentMandateId | JSON payload (clés triées)

4.3 Contenu des mandats

MandatSignataireContenu principal
IntentUtilisateurIntention NL, budget max, SKUs autorisés, mode (realtime/delegated), expiry
CartMarchandItems, sous-total, taxe (~8%), total, lien intentMandateId
PaymentUtilisateurMontant (= total panier), liens cart + intent

5. Flux utilisateur

5.1 Mode Realtime (utilisateur présent)

  1. L'utilisateur ajoute des produits au panier ou utilise l'IA.
  2. Checkout → le broker crée un Intent Mandate.
  3. Le broker appelle le Product Agent → Cart Mandate.
  4. L'UI affiche la revue de consentement (Review & pay).
  5. L'utilisateur approuve → Payment Mandate → broker valide → Payment Agent charge (mock).

5.2 Mode Delegated (utilisateur absent)

  1. L'utilisateur signe à l'avance un Intent Mandate avec conditions (budget, SKUs, dates).
  2. Un moniteur background (delegated-monitor.ts) surveille les conditions.
  3. Quand les conditions sont remplies, le broker exécute automatiquement cart + payment.

8. Architecture RAG (assistant shopping personnel)

Le RAG vit dans le broker (apps/broker/src/rag/). Il aide l'utilisateur à décider quoi acheter, sans créer de mandat ni payer.

8.1 Pipeline d'indexation (au démarrage du broker)

  MySQL Catalog (505 produits)
           │
           ▼
      CHUNKER (chunker.ts)
      1 produit = 1 chunk texte
      (nom, catégorie, SKU, prix, description)
           │
           ▼
   EMBEDDING MODEL (embeddings.ts)
   Xenova/all-MiniLM-L6-v2
   Vectorisation → vecteurs 384D normalisés
           │
           ▼
   VECTOR STORE (vector-store.ts)
   505 nœuds en mémoire
   Recherche par similarité cosinus

8.2 Pipeline de requête (runtime)

  Question utilisateur
           │
           ▼
   QUERY EXPAND (query-expand.ts)
   Ex: "aide sommeil" → + pillow, plush, comfort...
           │
           ▼
   Embed query → Vector search → Top-K chunks
           │
           ▼
   RERANK (rerank.ts)
   Filtre faux positifs (ex: train "Sleeping Car")
           │
           ▼
   AUGMENT + GENERATE (advisor.ts + groq-chat.ts)
   Contexte récupéré + question → Groq LLM
           │
           ▼
   Réponse : conseils + 1-3 picks (SKU, raison, prix)

8.3 Modules RAG

FichierRôle dans l'architecture RAG standard

embeddings.tsEmbedding model (vectorisation)
vector-store.tsVector store (index + recherche)
indexer.tsPipeline d'indexation complet

  • sub_search — recherche mots-clés dans le catalogue
  • sub_filter — garde uniquement les produits en stock

9.4 Cart Builder

Valide les SKUs, calcule sous-total + taxe, crée un Cart Mandate signé HMAC par le marchand (signerId: merchant), lié au Intent Mandate parent.

13. Sécurité et tests

13.1 Mécanismes de protection

  • Signatures HMAC sur chaque mandat
  • Validation de chaîne par le broker avant envoi au Payment Agent
  • Plafond de budget (maxPriceCents) dans Intent Mandate
  • Liste blanche SKU optionnelle (mode delegated)
  • Expiration temporelle des mandats
  • Protection replay (double paiement bloqué)
  • Authentification JWT sur toutes les routes sensibles

15.4 Scénarios à montrer à l'encadrant

  1. Parcours classique : parcourir le catalogue → ajouter au panier → checkout → approuver le mandat → paiement simulé.
  2. Assistant RAG : « What should I get as a gift under $30 for a kid who likes trains? » → Get advice → voir recommandations vectorielles.
  3. Achat par IA : « Buy noise-canceling headphones under $400 » → Search & review → modale consentement.
  4. Audit : consulter l'historique des commandes et la chaîne de mandats.
  5. Sécurité : npm run test:adversarial — démontrer le blocage des attaques.

15.5 Messages clés pour la soutenance

  1. « Le broker est le seul point de contrôle — aucun paiement sans mandat valide. »
  2. « L'utilisateur garde le dernier mot : même l'IA ne paie qu'après revue et approbation. »
  3. « Le RAG ne peut pas inventer de produits — il ne recommande que le catalogue indexé. »
  4. « Les agents Python exécutent ; le broker orchestre ; React présente le consentement. »
